# 予約確定の手動運用手順

新しい管理画面・確定APIは作っていません。既存のGoogleカレンダーとメール（手動送信）だけで運用します。
予約フォームからの申込は、すべて**未確定**としてカレンダーに登録されます。確定させるのはスタッフの手動操作です。

## 全体の考え方

- Webから届く申込は、カレンダー上で `[予約申込・未確定]` から始まるタイトルのイベントとして登録されます。
- タイトル・説明欄には**受付番号**（例: `WLG-A1B2C3D4E5`）が必ず入っています。同じ申込が再送された場合も、原則として同じ受付番号になります（詳細は「再送・重複の見分け方」参照）。
- イベントの説明欄には、受付番号・ステータス（未確定）・プラン・お名前・連絡先・初回利用か・ご相談内容が記載されています。
- **この未確定イベントは「予約が確定した」ことを意味しません。** スタッフが内容を確認し、対応できると判断した申込だけを、カレンダー上で手動で確定扱いに変更してください。

## 手順

### 1. 受付番号で再送・重複申込を確認する

- 同じ受付番号のイベントが複数ある場合は、それは「同じ申込操作の再送」です（通信エラー等でお客様が同じ内容をもう一度送った場合に発生し得ます）。新しい別の申込ではないため、重複として扱う必要はありません。
- **自分自身の未確定イベントを競合予約と誤認しないこと。** 同じ受付番号のイベントが2件あっても、それは「2人の別のお客様が同じ時間を取り合っている」わけではなく、「同じお客様の同じ申込が重複して記録された」状態です。内容（お名前・メール・受付番号）が完全に一致するかを必ず確認してください。
- 受付番号が異なり、かつ内容（お名前・連絡先・プラン等）も異なる場合は、別々の申込として扱ってください。

### 2. 既存の確定予約と、同じ時間帯の別申込を確認する

- その時間帯に他のイベント（`[予約申込・未確定]` または既に確定扱いにした予約）がないか確認してください。
- 受付番号が異なる複数の `[予約申込・未確定]` イベントが同じ時間帯にある場合は、**本当に別のお客様が同じ時間帯を希望している**ということです。先着・内容などスタジオの判断で、どちらを確定するか決めてください。

### 3. 対応できる申込だけをカレンダー上で「確定」に変更する

- 対応できると判断した申込は、そのイベントのタイトルを `[予約申込・未確定]` → `[確定]`（例: `[確定] 初回レコーディング体験 3時間 — 山田花子`）に手動で書き換えてください。
- 受付番号は説明欄に残したままにしてください（後から該当のお申し込みを追跡できるようにするため）。
- 必要であれば、このタイミングで初めてカレンダーの招待（attendees）を設定し、Googleカレンダーの通知機能を使っても構いません（システムからは自動送信されません）。

### 4. その後、顧客へ手動で確定連絡を送る

以下のテンプレートをコピーして、スタッフが手動で送信してください（システムからの自動送信はありません）。

{customerName} 様

受付番号: {receiptNumber}
プラン: {planName}
日時: {date} {time}〜（日本時間）

スタジオ所在地:
〒154-0011 東京都世田谷区上馬5-40-12 ラコルタ404

当日はご予約時間にお越しください。道に迷われた場合はご連絡ください。

担当 石川　080-8436-2412
```

```

Hi {customerName},

Your booking has been confirmed with the following details.

住所は、これまでの運用同様「確定後にご案内する」方針のまま、このタイミングで初めて伝えます。

### 5. 対応できない申込は別日程を相談し、不要な未確定イベントを整理する

- 対応できない申込には、Instagram DMまたはメールで別日程を相談してください。
- 相談の結果、その申込に対応しないことが決まった場合は、カレンダー上の該当する `[予約申込・未確定]` イベントを削除してください（残しておくと、その時間帯が「空いていない」と表示され続け、他のお客様が申込めなくなります）。
- 別日程で確定した場合は、新しい日時のイベントを作成するか、既存イベントの日時を修正して手順3・4を行ってください。

## 未確定イベントと空き状況の関係（重要）

- `[予約申込・未確定]` イベントも、確定済みイベントと同様に「空き状況」の判定では busy（空きなし）として扱われます。
- これは、同じ時間帯に次々と競合する申込が積み重なるのを避けるための運用判断です。ただしこれは**その時間帯を確保したことを保証するものではありません**（システムの表示・メール文面でも、受け付けた段階では「未確定」であることを明示しています）。
- そのため、対応しないと決めた申込の未確定イベントは、上記手順5の通り**早めに削除**してください。削除しないままだと、実際には空いている時間帯が、他のお客様には「空きなし」のまま表示され続けてしまいます。

## 通知メール送信失敗の確認

- カレンダーへの保存（申込受付）が成功しても、確認メールの送信だけが失敗することがあります。
- その場合、該当イベントの説明欄の先頭に `⚠️ 通知メール送信失敗（スタッフが手動で顧客へご連絡ください）` という目印が自動的に追記されます。
- この目印がある申込は、お客様に確認メールが届いていない可能性があるため、Instagram DMなど別の手段で受付完了をお知らせすることを検討してください。

## 残っている制約（今回解消していないこと）

- **同一プロセス内でのみ直列化**：空き確認〜カレンダー登録の排他制御（`lib/slot-lock.ts`）は、1つのサーバープロセス内でのみ有効です。Vercel等で複数インスタンスが並行稼働している場合、ごく短い時間差で同じ時間帯に複数の未確定申込が作られることがあります。ただし、これらは**自動で確定予約にはならない**ため、最終的な確定判断（手順1〜3）で人の目によって吸収されます。
- **受付番号そのものは決定論的**：同じidempotencyKey＋同じ内容であれば、どのプロセス・再起動後でも必ず同じ受付番号になります（lib/receipt.ts、メモリに依存しない純粋関数）。ただし「その受付番号の申込が既にカレンダーに存在するか」の検索（`findBookingByReceipt`）は、live/testモードでは実際の共有カレンダーを見るため複数インスタンスでも機能しますが、ごく短い時間差の競合まで完全には防げません。mockモード（ローカル検証専用）では各プロセスが独立した仮想カレンダーを持つため、プロセスをまたいだ重複防止は最初から対象外です。
- 以上により、**「複数インスタンス間の重複登録を完全に防止した」とは言えません**。今回の変更が解決したのは、「重複が起きても、それが自動的に確定予約として扱われてしまうこと」です。重複した未確定申込自体が発生する可能性は残っており、手順1・2の確認で見分けてください。
